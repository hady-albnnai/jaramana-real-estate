# إصلاحات تجربة المستخدم — التوثيق + خدمة التصوير + عروضي
**التاريخ:** 2026-07-25
**المصدر:** اختبار ميداني للمالك على جهاز Android حقيقي (دور: مستخدم عادي)

---

## 1) المشاكل المُبلغ عنها والأسباب الجذرية

### أ. "فشل في رفع صورة الهوية" عند الحفظ
- **السبب الجذري:** شاشة الهوية (`setup_identity_screen`) كانت ترفع الصورة **مباشرة** من العميل إلى bucket الخاص `ids_private`، بينما سياسات RLS على ذلك الـ bucket (migration `2026_06_07_advanced_security.sql`) تتطلب `auth.uid()` أي جلسة Supabase Auth حقيقية.
- مستخدمو التطبيق يعملون بنظام جلسات مخصص (`staff_session_token` عبر Edge Functions) فلا يملكون `auth.uid()` في طلبات التخزين المباشرة → الرفع يُرفض من السيرفر → الكود كان يبتلع الخطأ بصمت (`catch → return null`) ويعرض رسالة عامة.
- **الحل:** توحيد الرفع مع معمارية المشروع — رفع صور الهوية عبر Edge Function `user-account` بصلاحية `service_role` (نفس نمط `create-user` للموظفين `id_images_base64`).

### ب. رسالة التنبيه عن استكمال التوثيق غير واضحة
- عند الضغط على "طلب التوثيق الرسمي" وأي بيانات ناقصة، كانت تظهر SnackBar مؤقتة تختفي وتُربك المستخدم.
- **الحل:** إزالتها — الضغط يفتح شاشة الهوية مباشرة، وبداخلها تنويه ثابت وواضح: "لإكمال التوثيق يلزمك: ١) الرقم الوطني ٢) صورة بطاقة الهوية بالوجهين".

### ج. اختيار صور الهوية لا يسمح بتحديد الصورتين
- كان يوجد صندوق واحد لصورة واحدة فقط.
- **الحل:** زر "اختيار الصورتين معاً من المعرض" (multi-select بحدّ 2: الأولى أمامية والثانية خلفية) + صندوقا معاينة (أمامي/خلفي) يمكن استبدال كل منهما منفرداً (معرض/كاميرا).

### د. طلب تصوير العقار مخفي والمستخدم العادي لا يرى عروضه
- "طلب تصوير عقار" كان مدفوناً داخل قائمة الحساب كـ dialog بلا شرح للخدمة، ولا توجد أي شاشة تعرض للمستخدم حالة طلبه بعد الإرسال.
- شاشة `عروضي` (`/user/my-offers`) كانت موجودة بالكود لكن **لا يوجد أي زر يوصل إليها** للمستخدم العادي.
- زر إضافة عرض كان أيقونة `+` غير واضحة أعلى الشاشة الرئيسية.
- **الحل:** حسب اختيار المالك:
  - شريط سفلي بستة تبويبات: **الرئيسية، عروضي، طلباتي، مواعيدي، تصوير، حسابي**.
  - المفضلة انتقلت لأيقونة قلب أعلى الشاشة الرئيسية.
  - زر الإضافة نُزّل من الأعلى — "عرض جديد" موجود كـ FAB داخل "عروضي".
  - شاشة مستقلة `/user/photography` "خدمة التصوير العقاري": شرح مبسّط للخدمة + نموذج طلب + قائمة "طلبات التصوير الخاصة بي" وبحالتها.

## 2) التغييرات التفصيلية

### Edge Functions (تتطلب إعادة نشر)
| الدالة | الإضافة |
|---|---|
| `user-account` | action جديد `upload_id_images`: يستقبل `sid` + `front_b64`/`back_b64` (+`front_ext`/`back_ext`) → رفع لـ `ids_private` عبر service_role → تحديث `users.sid` و`users.img` (JSON array `[أمامي, خلفي]` عند الوجهين) → دمج مع الصور القديمة وحذف المستبدلة → فحص/إنشاء الـ bucket احتياطياً |
| `admin-photography` | action جديد `my_photo_requests`: يعيد مهام `photography_tasks` الخاصة بالمستخدم (`requested_by = uid`) بنفس منطق التحقق المستخدم في `request_photography` (JWT أو staff_session_token) |

## 3) صيغة التخزين
- `users.img`: مسار مفرد (توافق خلفي) أو `JSON.stringify([front, back])` عند الوجهين — نفس الاتفاق المعمول به في `create-user`.
- `ids_private` bucket يبقى خاصاً؛ العرض للإدارة بروابط موقّتة (60 ثانية) — دون أي تغيير أمني.

## 4) لا تغييرات على قاعدة البيانات
- لا جداول/أعمدة/سياسات جديدة (الـ bucket والسياسات موجودة في migration `2026_06_07`).
- لذلك لا حاجة لتحديث `supabase/setup.sql`.

## 5) خطوات النشر المطلوبة من المالك
```bash
supabase functions deploy user-account
supabase functions deploy admin-photography
```
ثم اختبار ميداني: توثيق حساب برقم وطني + صورتين، وطلب تصوير من تبويب "تصوير".

## 6) ملاحظة للمشرفين
- إذا كان لمستخدم ما قائمة صلاحيات مخصصة محفوظة (`users.perm` غير فارغة) قد لا يظهر له تبويب التصوير لأن قائمته لا تتضمن `user_photography` — الحسابات الافتراضية تحصل عليه تلقائياً.

## جولة 2 (2026-07-25 لاحقاً) — إغلاق حلقة طلب التصوير عند المكتب

تتبع نهاية-لنهاية للمسار كشف 3 فجوات تمنع اكتمال خدمة التصوير للطلبات القادمة من المستخدمين، وتم إصلاحها:

| # | الفجوة | الإصلاح |
|---|---|---|
| P1 | شاشة إدارة مهام التصوير كانت تحمل المهام باستعلام مباشر من العميل → محظور بـ RLS (جلسات مخصصة) → يرى المكتب قائمة فارغة ولا يعرف بطلب المستخدم | action جديد `list_tasks` في `admin-photography` (دور ≥ 3) + تحويل `PhotographyProvider.getAllTasks` ليستخدمه |
| P2 | لا يوجد مسار إسناد لطلبات المستخدم (بلا عرض): نموذج الإنشاء يتطلب عرضاً، ولا زر إسناد للمهام بانتظار | action جديد `assign_photographer` (يتحقق من أهلية المصور والحالة sts=0) + زر "إسناد مصوّر" على بطاقات المهام المعلّقة + شارة "طلب مستخدم" |
| P3 | زر "اعتماد وربط بالعرض" يفشل على الطلبات بلا عرض (`off_id = null`) | عند غياب العرض يُستخدم `update_status = 3` (اعتماد فقط) |
| P4 | المستخدم لا يرى الوسائط بعد الاعتماد | `my_photo_requests` يعيد `media` + عرض مصغّرات في بطاقة الطلب عند sts=3 |
| — | زر فتح العرض في بطاقة المهمة كان يسبب مساراً مكسوراً للطلبات بلا عرض | إخفاء الزر عند `offId` فارغ |

### تحسينات لاحقة مقترحة (غير منفذة)
1. إشعار فوري للمكتب عند وصول طلب تصوير جديد (حالياً الاكتشاف يدوي من شاشة الإدارة).
2. تنظيف `setup.sql`/`functions_dump.sql` من تعريف `create_photography_task_internal` القديم بأسماء أعمدة عتيقة (offer_id/assigned_by/title) وتوثيق الجدول الفعلي — حالياً الهجرة `2026_06_10_photography_tasks.sql` هي المرجع الحقيقي.
3. إضافة `user_photography` لقائمة الصلاحيات البيضاء في RPC القديم `admin_update_user_permissions` (المسار الفعلي عبر Edge Function لا يتأثر).
4. للمستخدم: خيار إلغاء طلب بانتظار.

## جولة 3 (2026-07-25 لاحقاً) — التحسينات المقترحة من التقرير

### 1) إشعارات فورية عبر جدول `notifications`
جميعها تُنفذ داخل `admin-photography` عبر `service_role`، وهي إجراءات ثانوية لا تكسر العملية الأساسية عند فشلها:
- **وصول طلب تصوير جديد** → إشعار لكل موظف نشط `role >= 3` (`act: photography_request_new`, tp=1).
- **إسناد مصور** → إشعار للمصور (`act: photography_task_assigned`, tp=2).
- **النتيجة النهائية (اعتماد/رفض/إلغاء)** → إشعار لصاحب الطلب، سواء عبر `update_status` (sts=3/4/5) أو `attach_media` (`act: photography_request_result`, tp=1).
- **إلغاء الطلب من صاحبه** → إشعار للمصور المُسند إن وُجد (`act: photography_request_cancelled`, tp=2).

### 2) إلغاء الطلب من المستخدم
- action جديد `cancel_photo_request` (مصادقة مستخدم كما في `my_photo_requests`): يسمح بالإلغاء فقط للمهام `sts = 0` المملوكة للطالب (يضبط sts=5 وts_done) → الزر يظهر في بطاقة الطلب المعلّق بشاشة خدمة التصوير، وبعده يمكن تقديم طلب جديد (فحص التكرار 0-2).

### 3) تنظيف `supabase/setup.sql`
- إضافة التعريف المرجعي الموحد لجدول `photography_tasks` وسياسات RLS (كان يفتقدها الملف — الهجرة كانت المرجع الوحيد).
- تصحيح `create_photography_task_internal` لأسماء الأعمدة الحقيقية (`off_id/requested_by/ttl` بدل `offer_id/assigned_by/title`).
- تصحيح `update_photography_task_status_internal` ليطابق المطبق فعلياً (تحقق 0-5 + `ts_done` عند الحالات النهائية).
- إضافة `user_photography` للقائمة البيضاء في `admin_update_user_permissions` القديمة.

## جولة 4 (2026-07-25 مساءً) — إصلاح رفع صور العروض + واجهة التحميل

### الخلل المُبلغ عنه
عند إضافة عرض: المستخدم يختار الصور → تظهر "جاري رفع الصور" ويُعد العداد → ثم يبقى المؤشر يدور للأبد دون إضافة العرض. والرسالة تظهر فوق المحتوى بشكل غير واضح.

### السبب الجذري (مركّب — طبقتان)
1. **السيرفر:** دالة `upload-offer-images` كانت تتحقق من `staff_session_token` بـ `p_min_role = 2` — أي أن المستخدم العادي (role=0) بدخول هاتفي (بدون JWT حقيقي) يُرفض دائماً 401 لكل صورة. الدالة لم تكن تعمل للمستخدمين العاديين إلا بحسابات الإيميل (JWT).
2. **العميل:** `StorageService.uploadOfferImages` يرمي استثناء عند فشل كل الصور — واستدعاؤه في `add_offer_screen._submit` **لم يكن داخل try/catch** (فقط `addOffer` كان محمياً) → استثناء غير ملتقط → `_submitting` تبقى true → سبينر لا نهائي. ولم تكن هناك أي مهلة زمنية على طلب الرفع.

### الإصلاح
| الطبقة | التعديل |
|---|---|
| `upload-offer-images` (سيرفر) | `p_min_role: 0` لتوثيق أي حامل جلسة صالحة، والتصنيف: `role >= 2` → موظف يرفع لأي مجلد؛ إلا → مستخدم عادي مقيّد بمجلده فقط (فحص `UNAUTHORIZED_FOLDER` الحالي يضمن الأمان) |
| `storage_service.dart` | مهلة 75 ثانية على طلب الرفع مع رسالة خطأ واضحة بدل التعليق اللانهائي |
| `add_offer_screen.dart` | رفع الصور صار داخل try/catch: فشل كامل → إيقاف المؤشر + عرض خطأ السيرفر الحقيقي + إلغاء (بدل النشر بلا صور رغماً عن المستخدم)؛ نجاح جزئي → نشر بالناجحة مع توضيح |
| الواجهة | مؤشر التحميل صار بطاقة داكنة أنيقة (إطار ذهبي + ظل) منفصلة تماماً عن محتوى الشاشة |

**ملاحظة:** الإصلاح السيرفري يفيد كل مسارات رفع الوسائط (إضافة/تعديل عرض، فيديو، سند ملكية) للمستخدمين العاديين بدخول هاتفي.
