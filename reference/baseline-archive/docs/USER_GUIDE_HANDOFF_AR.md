# ملف تسليم نظام دليل المستخدم

**المشروع:** المكتب العقاري الإلكتروني
**الفرع الحالي:** `arena/01a02e86-sweeda-real-estate-office-elc`
**الفرع المستهدف للمراجعة:** `main`
**تاريخ التسليم:** 2026-08-25

## 1. الغرض من هذا الملف

هذا الملف هو مرجع الاستئناف والتسليم للمحادثة أو المطور التالي. يشرح ما تم تنفيذه في نظام دليل المستخدم، وما تبقى، وكيفية متابعة العمل دون كسر وظائف التطبيق التجارية.

يجب قراءة الملفات التالية قبل أي تعديل:

1. `docs/USER_GUIDE_BALLOONS_MASTER_PLAN_AR.md`
2. `docs/USER_GUIDE_IMPLEMENTATION_STATUS_AR.md`
3. `docs/USER_GUIDE_START_HERE_AR.md`
4. هذا الملف

## 2. قاعدة العمل الإلزامية

نظام الدليل طبقة تعليمية مستقلة. لا يجوز أن يغيّر أو يعطل أو يعيد تنفيذ أي منطق تجاري قائم.

**ممنوع تعديل ما يلي لأجل الدليل:**

- الدفع والاشتراكات والتحقق من الدفع.
- الحجز والمواعيد والموافقة والرفض والإكمال.
- المطابقة والطلبات والعروض.
- Providers التجارية، خصوصاً:
  - `lib/providers/offer_provider.dart`
  - `lib/providers/request_provider.dart`
  - `lib/providers/appointment_provider.dart`
- SQL وSupabase migrations وEdge Functions.
- callbacks الأصلية للأزرار التجارية.
- صلاحيات المستخدمين وقواعد الملكية.

الربط المسموح هو إضافة `GuideAnchor` حول Widget حقيقي بشكل سلبي، أو استدعاء منسق الجولة بعد استقرار الشاشة. يجب أن يبقى callback الأصلي كما هو تماماً.

الاستثناء الأمني الوحيد الموثق في الخطة: إضافة `request_id` وIdempotency في طبقة الخادم لمنع التكرار، من دون تغيير منطق العمل أو الصلاحيات. هذا الاستثناء ليس جزءاً من مراحل الدليل الحالية.

## 3. المعمارية المعتمدة

- `GuideHost`: مالك عام واحد للدليل.
- `GuideController`: Controller مركزي واحد لكل التطبيق، مسؤول عن العرض والإخفاء ودورة الحياة ومنع التكرار.
- `GuidePresenter` و`OverlayEntryGuidePresenter`: طبقة العرض القابلة للاستبدال.
- `GuideOverlay` و`GuideVisualPrototype`: التعتيم والهدف والفقاعة.
- `GuideAnchor`: تسجيل Widget حقيقي وقياس Rect الخاص به.
- `GuideTargetRegistry`: سجل الأهداف وقياسها والتحقق من الحجم.
- `GuideStorage`: تخزين محلي scoped حسب الدور و`uid` ونسخة المحتوى.
- `GuideCopy`: المصدر الوحيد للنصوص المعتمدة.
- منسقات منفصلة حسب الدور:
  - `visitor_guide_coordinator.dart`
  - `user_guide_coordinator.dart`
  - `broker_guide_coordinator.dart`

لا تستخدم E2E كمرساة بصرية. يجب استخدام `GuideAnchor` أو `GlobalKey` لكل هدف بصري.

## 4. المواصفة البصرية والسلوكية

- بطاقة بيضاء شبه شفافة بعتامة تقريبية 96%.
- تعتيم خلفي أسود تقريبي 20%.
- لون العنوان `#17130A`.
- لون المحتوى `#6F6656`.
- لون الزر الذهبي `#D4AF37`.
- زوايا البطاقة 24px.
- زر الإغلاق ومساحة اللمس لا تقل عن 48px.
- زر الإجراء الافتراضي بارتفاع 52px.
- ظهور 260ms وإعادة تموضع 220ms بمنحنى `easeOut`.
- لا وميض ولا نبض ولا توهج مستمر.
- دعم RTL وSafeArea والكيبورد والنص الطويل.
- الهدف تعليمي وغير تفاعلي أثناء الشرح؛ لا ينفذ ضغطاً على وظيفته.
- سؤال البداية والشرائح لا يستخدمان سهماً.
- البالون المرتبط بهدف يستخدم السهم والتعتيم.
- زر `×` يغلق الخطوة ولا يسجلها مكتملة.
- «تخطي الجولة» يحتاج تأكيداً.
- الاهتزاز فقط عند التالي أو الإنهاء أو تأكيد التخطي.
- الخلفية معزولة لقارئ الشاشة، مع Semantics وFocus مناسبين.

## 5. ما تم إنجازه

### P0 إلى P6

تم تنفيذ واختبار:

- النموذج البصري الأولي.
- نماذج الحالات والنسخ والأدوار والخطوات.
- التخزين المحلي scoped ومعالجة السجلات التالفة.
- Registry وAnchor وقياس الأهداف.
- Presenter وOverlay ومنع وجود Overlayين.
- Controller وHost وLifecycle وIdempotency.
- سؤال البداية والشرائح والتقدم والرجوع والتخطي والإغلاق.

### P7 — جولة الزائر

مكتملة ومعتمدة.

المسار:

```text
/home
→ انتظار استقرار إذن الإشعارات
→ سؤال جولة الزائر
→ ثلاث شرائح
→ بالون تصفح العروض
→ عد عرضين مختلفين
→ بالون الفلاتر
→ المشاركة في تفاصيل العرض
```

تم أيضاً إضافة زر `?` المؤقت بعد الرفض، والعنوان الديناميكي للمكتب، وfallback آمن للعنوان، ومعالجة حالات فشل الأهداف.

آخر اعتماد سابق:

```text
ca98e23 P7: اعتماد نجاح جولة الزائر
```

### P8 — جولة المستخدم

مكتملة ومعتمدة بعد تأكيد نجاح:

```text
flutter analyze
flutter test test/guide
```

المسار:

```text
تسجيل الدخول
→ /setup-profile للمستخدم الجديد
→ /user/home بعد الحفظ
→ انتظار استقرار الشاشة
→ سؤال جولة المستخدم
→ ثلاث شرائح
→ بالون عروضي
→ بالون طلباتي
→ بالون مواعيدي
```

التنفيذ:

- `lib/core/guide/user_guide_coordinator.dart`.
- شرائح المستخدم في `GuideCopy.userIntroSlides`.
- أهداف حقيقية لتبويبات الشريط السفلي، وليست E2E فقط.
- تخزين مستقل حسب `uid`.
- زر `?` للمستخدم.
- عدم تشغيل الجولة أثناء `setup-profile`.

اعتمادات P8:

```text
d0e36f7 P8: بدء جولة المستخدم
a8cd2cc P8: إصلاح أخطاء تحليل منسق المستخدم
e9d8635 P8: اعتماد نجاح جولة المستخدم
```

### P9 — جولة الوسيط

بدأ تنفيذها، لكن لا تعتبر مكتملة حتى ينجح التحليل والاختبار وتجربة التطبيق الفعلية.

المسار المعتمد:

```text
حساب وسيط معتمد brk=1
→ ظهور /broker/dashboard مستقراً
→ سؤال جولة الوسيط
→ بالون واحد فقط بعنوان مزايا الوسيط
→ زر فهمت
```

النص المعتمد لا يذكر ميزات غير مثبتة مثل أولوية الظهور أو شبكة عملاء أوسع. البالون يذكر فقط:

- حتى خمسة عروض.
- حتى خمسة طلبات.
- لوحة وسيط خاصة.
- الإعفاء من عمولة المكتب.

التنفيذ الحالي:

- `lib/core/guide/broker_guide_coordinator.dart`.
- هدف حقيقي بعنوان «الأقسام» في `broker_dashboard_screen.dart`.
- دعم `actionLabel` مخصص حتى يظهر زر «فهمت» بدلاً من «إنهاء الجولة».
- تخزين مستقل حسب `uid`.
- زر `?` للوسيط.

آخر Commit لـP9:

```text
62db8a4 P9: إصلاح أخطاء تحليل جولة الوسيط
```

يجب إعادة تشغيل التحليل والاختبارات بعد هذا Commit. كانت الأخطاء التي ظهرت سابقاً في P9 هي أخطاء compile/analyze وتم إصلاحها، لكن لا يعتمد الإغلاق قبل تأكيد المطور على الجهاز.

## 7. ما تبقى

1. تشغيل:

   ```cmd
   flutter analyze
   flutter test test/guide
   ```

2. تجربة P9 فعلياً بحساب وسيط معتمد:
   - السؤال يظهر بعد استقرار `/broker/dashboard`.
   - الضغط على «لا، شكراً» يحفظ الرفض ولا يعرض البالون مباشرة.
   - الضغط على «نعم، ابدأ» يعرض بالون «مزايا الوسيط».
   - زر البالون هو «فهمت».
   - إعادة الجولة من `?` تعمل ضمن مدة المساعدة.
   - لا تظهر جولة المستخدم للوسيط.

3. عند النجاح، تحديث `docs/USER_GUIDE_IMPLEMENTATION_STATUS_AR.md` إلى P9 مكتملة، ثم Commit مستقل وPush.

4. المراحل اللاحقة:
   - P10: الصلابة وAccessibility.
   - P11: الاختبار النهائي والتسليم.

ومن P10/P11 يلزم اختبار حالات lifecycle، تغيّر الدور، غياب الهدف، النص الطويل، الإغلاق المتكرر، Reduce Motion، قارئ الشاشة، واختبارات فتح/إغلاق متكرر. لا تعتبر E2E وحدها اختباراً بصرياً.

## 8. طريقة العمل الإلزامية لكل مرحلة لاحقة

1. قراءة الخطة وسجل الحالة قبل التعديل.
2. التأكد من الفرع:

   ```cmd
   git branch --show-current
   ```

   ويجب أن يكون:

   ```text
   arena/01a02e86-sweeda-real-estate-office-elc
   ```

3. تعديل المرحلة الحالية فقط.
4. عدم تعديل الوظائف التجارية أو callbacks الأصلية.
5. إضافة الاختبارات قبل اعتماد المرحلة.
6. تشغيل:

   ```cmd
   flutter analyze
   flutter test test/guide
   ```

7. تجربة المسار الفعلي عند طلب الخطة ذلك.
8. تحديث سجل الحالة بالعربية.
9. إنشاء Commit مستقل باسم واضح.
10. Push إلى فرع الجلسة فقط.
11. لا تنتقل للمرحلة التالية عند وجود أي error أو فشل في معيار الخروج.

## 9. آلية الدمج

لا يُدفع مباشرة إلى `main` أثناء جلسة Arena. تتم المحافظة على كل العمل في فرع الجلسة، ثم يُفتح Pull Request من هذا الفرع إلى `main` للمراجعة والدمج الآمن. بعد الدمج، يستطيع أي استئناف لاحق قراءة هذا الملف من `main` أو من الفرع المرفوع.

قبل الدمج يجب أن تكون حالة الاختبارات واضحة، وألا يحتوي PR على تعديلات تجارية غير مرتبطة بالدليل.

## 10. تحذير نهائي للمطور التالي

لا تعِد بناء وظائف التطبيق داخل نظام الدليل، ولا تجعل البالون ينفذ ضغطاً على الهدف، ولا تستخدم Widget E2E كمرساة بصرية، ولا تبدأ الجولة قبل استقرار المسار، ولا تخلط تخزين الزائر بالمستخدم أو الوسيط، ولا تضف نصوصاً تسويقية غير معتمدة، ولا تعتمد مرحلة قبل نجاح التحليل والاختبارات وتجربة معيار الخروج.
