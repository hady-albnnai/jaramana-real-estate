## 🚨 قسم صفري: ثغرة أمنية حرجة اكتُشفت أثناء التخطيط

### VULN-001 — نموذج الصلاحيات ينهار مع الدورين 7 و8

**الخطورة**: 🔴🔴 **حرجة — تصعيد امتياز مؤكَّد حياً**
**الحالة**: مفتوح — يحتاج قرار المالك قبل الإصلاح

#### جذر العطل

نموذج الأدوار **تسلسلي** (`role >= minRole`)، وهذا صحيح للأدوار 0→6:

```
0 مستخدم < 1 وسيط < 2 مصور < 3 مشرف < 4 موظف < 5 نائب < 6 مدير
```

لكن الدورين **7 محامٍ** و**8 معقّب** أُضيفا **فوق** المدير رقمياً، بينما هما
**تخصّصان جانبيان لا رتبتان أعلى**. النتيجة: كل تحقق في النظام مبني على
`role >= N` يمرّ لهما تلقائياً.

المصدر: `validate_staff_session` في القاعدة:
```sql
IF v_user.role < p_min_role THEN
  RETURN jsonb_build_object('success', false, 'error', 'UNAUTHORIZED');
END IF;
```
`7 < 5` = false ⇒ يُمرَّر. `8 < 5` = false ⇒ يُمرَّر.

> **تنويه**: البند 3-8 رُفضت برسائل مثل
> `Could not find the function ... (p_admin_uid)` — أي أن **بوابة الصلاحية
> مُرِّرت** ووصل الطلب إلى استدعاء الدالة، والفشل جاء من نقص معاملات
> (خطأ في نصّ اختباري) لا من الأمان. البند 8 أوضح دليل: وصل إلى التحقق
> التجاري (صور الهوية) بعد اجتياز كل فحوص الأمان.

**تنظيف**: أُعيد `contactPhone1` إلى `0933713023` فوراً، وأُلغيت كل الجلسات
التجريبية، ولم يُنشأ أي مستخدم (تحقُّق: `count = 0`).

#### لماذا لم يُكتشف سابقاً؟

الواجهة تخفي الأمر: `app_router.dart:219-221`
```dart
if (path.startsWith('/admin')) {
  if (auth.isLawyer) return '/lawyer/dashboard';    // يُعاد توجيهه
  if (auth.isExpediter) return '/expediter/tasks';  // يُعاد توجيهه
```
فالمحامي **لا يرى** شاشات الإدارة. لكن الحماية **بالواجهة فقط** — وأي نداء
API مباشر (curl، تطبيق معدَّل، أداة اعتراض) يتجاوزها بالكامل.

`PermissionService.defaultsForRole(role)` تزيد الطين بلة:
```dart
permissions.where((p) => role >= p.minimumRoleForDefault)
```
⇒ محامٍ (7) و معقّب (8) يحصلان تلقائياً على **كل** صلاحيات المدير الافتراضية،
لأن أعلى `minimumRoleForDefault` هو 6.

**تحقُّق حي**: الأربعة (محاميان + معقّبان) لديهم `perm = []` — أي **لا تخصيص
يدوي**، فهم يعتمدون كلياً على الافتراضي المعطوب.

#### الخيارات المقترحة (تحتاج قرار المالك)

| # | الحل | المزايا | المخاطر |
|---|---|---|---|
| **أ** | **سقف علوي**: تغيير كل `role >= N` إلى `role >= N AND role <= 6` | إصلاح جذري بمكان واحد (`validate_staff_session`) + `PermissionService` | يجب مراجعة كل موضع لا يمرّ عبر الدالة |
| **ب** | **إعادة ترقيم**: المحامي 2.5 والمعقّب 2.6 (أو نقلهما تحت 3) | يُصلح التسلسل منطقياً | **يتطلب ترحيل بيانات** وتعديل كل مرجع للرقمين — خطر عالٍ |
| **ج** | **فصل التخصص عن الرتبة**: عمود `specialty` منفصل عن `role` | الأنظف معمارياً وطويل الأمد | أكبر تغيير — ليس قبل النشر |

**توصيتي**: **(أ) الآن** — إصلاح دقيق منخفض المخاطر يُغلق الثغرة قبل النشر،
ثم **(ج) لاحقاً** بعد الاستقرار.

**⚠️ استثناء يجب مراعاته**: المدير الرئيسي Hady (role=6) يجب أن يبقى قادراً
على كل شيء. والمحامي يحتاج فعلاً وصولاً إلى `legal-actions` (min_role=0)
و`get-staff-id-images` — فالسقف يجب أن يكون **لكل دالة** لا عالمياً.
